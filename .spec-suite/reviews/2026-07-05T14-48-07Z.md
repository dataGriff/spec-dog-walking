# Adversarial Spec Critique — dog-walking spec set

- **Run:** 2026-07-05T14:48Z
- **Method:** four independent adversarial review passes (PRD↔contracts traceability; cross-contract consistency; domain model/glossary/scenarios/flows; auth/errors/NFRs), findings deduplicated and verified against file evidence. Complements — does not replace — the `domain-review` qualitative categories.
- **Result:** 44 consolidated findings (10 high, 20 medium, 14 low) from 62 raw findings. Substantial clean surface too — see "Verified clean" at the end.
- **Purpose:** feed systemic root causes back into `domain-spec-suite` (gate hardening tracked there as v1.0.14 / gate 1.1).

---

## High

### H1. Unreturnable error codes — the catalogue promises codes the contract cannot emit
`INVALID_WALK_TYPE`, `INVALID_PHOTO`, `NO_BILLABLE_WALKS` are 400s in the catalogue (error-catalogue.md:299-342) and asserted by scenarios (acceptance-scenarios.md:283-284, 453-454, 523-524), but every 400 response on their trigger operations refs `ValidationError`, whose `code` enum is exactly `[VALIDATION_ERROR]` (openapi.yaml:634-640; operations at openapi.yaml:292, 400, 461). The codes exist only in the `Error` schema enum, which is bound to 401/403/404/409/410 responses only (openapi.yaml:572-597, 629-631). Similarly `IDEMPOTENCY_KEY_CONFLICT` (error-catalogue.md:196-212) is cited by the `Idempotency-Key` param description (openapi.yaml:554-558) but missing from the `Error.code` enum, and no operation declares a 409 for it. A compliant server cannot satisfy the spec.

### H2. NFR-mandated 429 exists nowhere downstream
nfr.md:126-132 requires `429 Too Many Requests` on auth endpoints; no `RATE_LIMITED`-style code in the catalogue, no 429 response in openapi.yaml.

### H3. Daily reminders: core PRD goal with zero contract coverage
The problem statement and Goal 1 make daily reminders first-class (prd.md:6-7, 16, 63-64). No user story, endpoint, or channel covers them. A stated product goal is untestable against the contracts.

### H4. Walker onboarding was invented at contract time and is broken end-to-end
`POST /v1/auth/register` (openapi.yaml:40-65) traces to no PRD story (auth stories are US-001–US-004, prd.md:91-143), has zero acceptance scenarios, and Flow 1 sends `{email, password, role}` while `RegisterRequest` has no `role` and requires `displayName` (sequence-diagrams.md:19 vs openapi.yaml:660-666). error-catalogue.md:125-126 references the nonexistent `role` field.

### H5. Walker is invisible to the historic record — dangling FKs in four tables
No `walker.*` event channel (asyncapi.yaml:55-133) and no `walker` datacontract table, yet `invite.walkerId`, `walk.walkerId`, `ratecard.walkerId`, `invoice.walkerId` all reference it (datacontract.yaml:56, 324, 374, 402). Consumers can never resolve `walkerId` from the stream, contradicting the "reconstruct without re-querying the API" claim (asyncapi.yaml:14-17). Root cause: channels derive from the model's Domain Events table, Walker has no creation event, and the write-op→channel check exempts `/v1/auth/*` paths. `User` has the same problem (openapi.yaml:698-714 vs datacontract.yaml:71).

### H6. Client-creation timing contradicted three ways — and one version is schema-impossible
openapi says Client exists at invite time (`addClient` 201 returns `clientId`, openapi.yaml:166-170) with **required** `userId` (openapi.yaml:726-735); domain-model.md:80 says Client is created at invite **acceptance**; glossary.md:26-27 says at **invite**. A Client created before acceptance cannot have the required `userId` — `listClients` would return schema-invalid rows for pending invitees.

### H7. "Walks keep their recorded price" invariant has no recording mechanism
domain-model.md:254-255 and :336-348 pin invoice line prices to the rate in force at the walk's `scheduled` transition, but Walk carries no price field (openapi.yaml:1093-1113) and `PUT /v1/rate-card` wholesale-replaces entries (openapi.yaml:1194-1207), destroying history. No scenario tests invoicing after a rate change.

### H8. Refresh token is dead surface
`AuthResponse` returns `refreshToken` (openapi.yaml:689-695), NFR-SEC-001 fixes its 30-day lifetime (nfr.md:106-110), US-004 revokes it to "force re-login" (prd.md:142-143) — but no refresh or logout endpoint exists, and auth-matrix.md:16-20 declares refresh out of scope. The token is unusable, so revoking it forces nothing; the lifetime NFR is untestable.

### H9. Invite lifecycle states unreachable from events
datacontract pins `invite.status` to `[pending, accepted, expired]` (datacontract.yaml:58) but the only invite channel is `invite.created` (necessarily `pending`); `acceptInvite` emits only `ClientRegistered`, and nothing emits on expiry. Two of three states can never appear in the historic record.

### H10. Untestable scenario: US-004-B asserts unobservable revocation
"every refresh token previously issued for that user is revoked" (acceptance-scenarios.md:129) has no observable contract surface (no refresh/introspection endpoint; RefreshToken isn't a modelled entity despite rules depending on it, domain-model.md:135-137).

## Medium

### M1. Rate-card currency shape is inconsistent across the round trip
Request: per-entry `currency` required (openapi.yaml:1202-1207, per prd.md:364-366). Response entity, event envelope, and datacontract: single root-level currency, no per-entry field (openapi.yaml:1171-1193; asyncapi.yaml:509-518; datacontract.yaml:373-377). Model additionally says currency is card-level and immutable (domain-model.md:261-268) with no error code for change attempts. Mixed-currency PUTs are accepted but unrepresentable.

### M2. Decline reason: optional in PRD/openapi, required in the event
prd.md:222-223 and openapi.yaml:1123-1128 make `reason` optional; `WalkDeclinedEnvelope` requires non-nullable `declinedReason` (asyncapi.yaml:375, 386); datacontract.yaml:331 says required: false. A reason-less decline emits an event that fails its own schema.

### M3. Breed vocabulary: three contracts, three strategies
PRD leaves breed a plain optional string (prd.md:150-151). The contract invents a ~211-value UK Kennel Club enum (openapi.yaml:806-1039), duplicated closed into datacontract (datacontract.yaml:87-304), while asyncapi downgrades to bare `string` (asyncapi.yaml:215-219). The enum is declared open in openapi (additions = minor bump, openapi.yaml:808-816) — an addition would pass API and event but violate the pinned data contract. The "UK Kennel Club" scoping was never escalated to the PRD or Decision Log.

### M4. `listInvoices` drops the `from`/`to` filters US-015 requires
prd.md:334 vs openapi.yaml:469-472 (only page/pageSize/status); `listWalks` carries them faithfully (openapi.yaml:304-305). Also US-015's "balance owed" (prd.md:330-331) has no field anywhere (openapi.yaml:1209-1250).

### M5. `ClientRegistered` omits `inviteId` — invite→client lineage unjoinable from events
asyncapi.yaml:268-275 / datacontract.yaml:70-75 vs REST returning both ids together (openapi.yaml:742-747). Only a fuzzy email join remains.

### M6. Dangling `ref:` pointers in datacontract
`#/components/schemas/...` refs at datacontract.yaml:58, 92, 328, 330, 332, 359, 408 — datacontract.yaml has no `components` section; refs implicitly mean openapi.yaml but are unresolvable as written.

### M7. Scenario literals violate the contracts they test
US-005-A sends breed `Border Collie` — enum value is `border-collie` (acceptance-scenarios.md:151 vs openapi.yaml:1009). US-004-B's `newPassword "fresh!"` is 6 chars vs `minLength: 8` (acceptance-scenarios.md:127 vs openapi.yaml:683). Both scenarios assert success.

### M8. Systemic response-path drift in scenarios and flows
Scenarios assert wrapped keys (`dog.*`, `walk.*`, `invoice.*` — e.g. acceptance-scenarios.md:154, 197-198, 342, 511-513) while contracts return bare entities; diagrams use `dogId`/`walkId`/`age` keys where schemas use `id`/`ageYears` (sequence-diagrams.md:133-134, 156, 195, 231 vs openapi.yaml:1066).

### M9. Idempotency-Key required on every POST, supplied by no scenario
Strictly read, every POST scenario should 400. No scenario tests replay or key conflict either.

### M10. Walk `requested → cancelled` contradicted between model prose, lifecycle table, and auth matrix
"Either party" (domain-model.md:199-200) vs owner-only trigger annotation (domain-model.md:435, 442) vs unconditional walker cancel (auth-matrix.md:44). No scenario cancels a `requested` walk.

### M11. Four events trace to nothing in the PRD
`InviteCreated`, `ClientRegistered`, `DogAdded`, `RateCardUpdated` (asyncapi.yaml:56-73, 116-121) — plausible under the suite's events-doctrine but the PRD was never back-filled; they cascade into three datacontract tables.

### M12. Coverage gaps: operations, transitions, and error paths with no scenario
`listClients`, `listDogs` (also traced to no story); `acceptInvite` 409; `RESET_TOKEN_ALREADY_USED`; >5-photos and wrong-MIME `INVALID_PHOTO` variants; `AUTHENTICATION_REQUIRED`/`TOKEN_EXPIRED`; walker-initiated cancel; posting an update on a completed walk; pagination on any list.

### M13. Never-existed tokens have no defined response
`acceptInvite` / `confirmPasswordReset` with an unknown token: no 404, `Gone` covers only expired/used, `RESOURCE_NOT_FOUND` scopes itself to path-id routing (openapi.yaml:137-149, 118-121; error-catalogue.md:81-95, 218-274).

### M14. No error code for invalid-signature/tampered JWT
Catalogue 401s cover only missing header and expiry-with-valid-signature (error-catalogue.md:20-31); the most common real 401 is unmapped.

### M15. Body-referenced-id not-found unspecified for three creates
`scheduleWalk` (`dogId`), `generateInvoice` (`clientId`), `addDog` (`ownerId`) declare no 404; implementers can't decide 404/403/400 for nonexistent body ids (openapi.yaml:286-294, 455-463, 210-218).

### M16. 403/404 split is a resource-existence oracle
Cross-tenant access → 403, nonexistent → 404 (auth-matrix.md:70-73): UUID probing distinguishes "exists but not yours" from "doesn't exist". The 403-vs-404 tenancy decision was never explicitly made.

### M17. Invite acceptance excluded from rate limiting → invite-token brute force
NFR-SEC-004 covers four endpoints (nfr.md:128-129); `POST /v1/invites/{token}/accept` is public, token-authenticated, format-unconstrained (openapi.yaml:126-131). Security-relevant.

### M18. No GDPR / data-subject-rights NFR despite substantial UK PII
Owner contact details, vet phone, dog medication stored; retention has floors but no ceilings; deletion deferred wholesale (nfr.md:159-179).

### M19. NFR-AVAIL-002 (best-effort event delivery) contradicts asyncapi's audit-grade completeness claim
nfr.md:76-79 vs asyncapi.yaml:12-17.

### M20. Rate-card ownership rule references a parameter that doesn't exist; singleton has no empty state
auth-matrix.md:77-79 gates on "the requested Walker" but `GET /v1/rate-card` takes no walker id; only 200 declared before any PUT (openapi.yaml:528-540).

## Root-cause synthesis → suite actions

The findings cluster into systemic causes in the generating tool, not one-off authoring slips:

1. **Checks validate mirroring of what exists, not closure or reachability.** Nothing verifies a catalogue code is *emittable* (H1, H2), an FK is *resolvable* from the event stream (H5), an enum state is *reachable* (H9), or a `ref:` *resolves* (M6). → New checks: ERROR-CODE-REPRESENTABLE, EVENT-FK-RESOLVABLE, DATACONTRACT-REFS-RESOLVE.
2. **Traceability is one-directional.** Stories→flows is checked; operations→stories/scenarios is not (H3, H4, M11, M12). → New checks: OPERATION-HAS-SCENARIO; entity-has-event at modeling (catches H5 upstream).
3. **Scenario literals are never validated against contracts** (M7, M8, M9, H10). → New check: SCENARIO-REFS-VALID; scenario-authoring conventions in template.
4. **Placeholder check too narrow** (L4). → extend to TODO/TBD/FIXME.
5. **Invented vocabulary and invented endpoints aren't escalated** (M3, H4): skill instructions must force Decision Log entries / PRD back-fill for contract-time inventions.
6. **Template blind spots**: no privacy/DSR NFR category (M18), no 429/rate-limit slot (H2), no invalid-signature or never-existed-token error stubs (M13, M14), no singleton-resource ownership pattern (M20), no 403-vs-404 tenancy decision prompt (M16).

These are being implemented in `domain-spec-suite` (BUILD-PLAN §6.19, gate 1.1). Spec-set fixes for the findings themselves should follow via update mode after the suite upgrade, so the new gates verify the fixes.
